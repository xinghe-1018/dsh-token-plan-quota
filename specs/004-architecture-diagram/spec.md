# 004 — 架构图入库

来源：2026-09-18 会话（003 合入 main 之后）。用户先要"给项目做一张示意图"，再要"放到仓库"。
图本身已经存在且已验收：`dsh-token-plan-quota` 的 architecture 示意图，由 Archify 技能生成，
showcase 档 9/9 项检查通过、0 error / 0 warning，并在 1440×900 / 1600×1000 / 1920×1080 / 2048×1320
四档实测无溢出（实测方法见 `plan.md` 前提 6）。本规格要解决的是**它现在放在哪、以什么形态入库、
以及入库之后靠什么守住**——不是"再画一张图"。

## 为什么现在做

1. **仓库对外只有"文字 + UI 截图"，没有一张讲结构的图。** README 现有 13 张图全是运行时界面的
   截图（徽标、面板、各状态卡），读者要知道"宿主半边 / 浏览器半边 / 只读接口面 / 五个上游源"
   怎么串起来，只能通读 3 万字 README。结构图是唯一缺的那一类。
2. **图已经在仓库外产生，且不是随手产物。** 它有可编辑的源规格（JSON）、有确定性验收记录
   （四档实测 + 成品哈希）。按项目立场"没有证据的声称只有一个回应：跑一遍给我看"，它已经跑过了；
   不进仓库等于把已经付过的成本留在草稿区。
3. **不落门禁就等于会漂。** 本项目对"散文规则"的既定立场是：能机械化的一律做门禁。
   图进了仓库而没人管它是否存在、是否随包发布，那么第一次清理目录就会被顺手删掉，
   而 README 里那条链接会静默变成破图。

## 功能需求

- **FR-001**（资产入库）仓库内有一份可发布的架构图资产，README 用**相对路径**引用它。
  验收：GitHub 与 npmjs 两处都能渲染（相对路径 + 资产在 `package.json#files` 白名单内），
  且 `check-docs` 的"发布面"检查（链接目标必须随包发布）继续通过。

- **FR-002**（单一真源）图**不是手绘的一次性图片**：它的源规格（Archify architecture JSON）随仓库保管，
  并有一份说明写清再生成的前置条件与命令。验收：另一个人按说明能重新产出同一张图；
  说明里必须写明"再生成是**开发动作**，不进 CI"，理由是它需要仓库之外的 Archify 技能与 Chromium。

- **FR-003**（门禁）图的存在性进 `check-docs` 第 10 项的清单（该清单目前硬编码 13 条截图路径）。
  验收：图存在→绿；把图删掉→**必红**，并贴出红的那一次输出（可证伪，不是"我读了代码觉得会红"）。

- **FR-004**（双语同源）`README.md` 与 `README.en.md` 在同一次改动里加同一张图与同源图注，
  不得只在一侧出现。验收：两处引用都过 `check-docs`；图注措辞在两侧**语义一致**（不是逐字翻译）；
  并且 `check-docs` 里有一条**点名断言**要求两份 README **真的引到**它——判"引用"用
  `mentionsTarget`：归一化相对路径 / `<img src>` / 引用式定义 / 绝对 GitHub 链接都算，
  代码围栏里的示例与 HTML 注释里的引用不算（行为矩阵常驻 `test/guards.mjs`）。

- **FR-005**（零影响）本次**不改变任何运行时行为**：`lib/` 不动、不新增任何依赖（宪法 IV）、
  `npm run check` 七步全绿、CI 三平台矩阵（node 20/22 × ubuntu/windows/macos）不受影响。
  验收：贴出最后一次编辑之后的 `npm run check` 输出。

- **FR-006**（图必须与代码同源）图上每个节点与每条关系都要能指到代码里的出处
  （`lib/index.js` 的源目录、`lib/detect.js`、只读路由面、`lib/client.js`）。
  图上不得出现代码里不存在的能力、也不得把"明确不做的三类"画成已支持。
  验收：`plan.md` 的前提表里逐条列出处；三份 lens 评审各自独立核一遍。

## 非目标

- **不改 `lib/` 与任何运行时行为**：文档层只加资产、加一条存在性清单项、**加一条点名断言**、
  把一条规则写精确。（点名断言原先不在本非目标里，是评审 Lens 3 的 MEDIUM，工件已在同轮回写。）
- **不把结构图加进 `screenshots.json`**：那个文件是"向插件市场声明截图与展示顺序"的**策展子集**
  （`docs/images/` 有 13 张，它只列 7 张，英文套一张没列），本来就不是全集，因此不存在"必须同步"的义务。
  是否让它上市场是一个产品决策，本 PR 明确不做（原先工件通篇未提它，属默默跳过，评审 Lens 3 点出后补记）。
- **不把交互式 HTML 入库**：交付的 `dsh-token-plan-quota-architecture.html` 是 642 KB 的独立查看器，
  它不是文档资产，是生成器的输出。入库的是**位图 + 源规格 + 再生成说明**。
- **不动 `docs/images/` 下那 13 张 README 截图、也不动 `scripts/shots/make-shots.mjs`**：
  那些图有明确的唯一产出方（截图流水线），本次不改变它们的任何行为。
- **不手绘、不重画 SVG**：实测交付 HTML 里的 `<svg>` 依赖查看器页面的 CSS 类（无内联样式），
  直接抽出会丢配色与字体；本次不为了"矢量"去做一次有保真风险的重建（取舍见 `plan.md` §4）。
- **不新增依赖、不改宪法、不改 `CHANGELOG.md`、不改 `reviews/`**：理由与 003 同（历史与冻结证据不动）。
- **不做发布动作**：版本号、CHANGELOG 段落、npm 发布由 `scripts/release.mjs` 的流程负责，
  本次只在 main 的下一轮发布里自然带上这张图。

## 与既有规格的关系

001/002 修的是"文档说的和代码不一致"，003 修的是"发现不一致的机制本身不可靠"。
004 补的是**一类从未入库的文档资产**，因此它的门禁落点也最小：只在既有的第 10 项清单上加一条，
不新建独立检查进程（新建进程会引入"入口判定静默不执行"那一类风险，而这里的收益不值得那个成本）。
`specs/001..003` 的工件与其 `reviews/` 保持原样。
