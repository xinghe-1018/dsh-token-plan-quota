# 003 — 计划

## 0. 修订

- **初版被推翻的思路**：FR-001 一开始想"把 `now` 钉成一个固定值再断言"。否决理由见 §4 的
  「Chosen approach and why」——那等于让守卫去验一个**真实出图时不存在**的 payload。
- **第二轮（评审后）**：Lens 2/3 的发现改变了若干数字与取证方法，本文件已按实测改写
  （改动点见 §10）。凡是曾被写错的地方都保留纠正后的口径**与取证方式**，因为"这个数字怎么来的"
  比数字本身更容易出错。
- **第三轮（收口）**：`tasks.md` 的勾选、`test/guards.mjs` 与 `scripts/link-targets.mjs`
  这两件产物是评审指出"计划里没有"之后补进来的。

## 1. Problem

001/002 两轮实践会话的 retro 结论：**真正吃掉时间的不是判断失误，而是护栏自身的缺陷**。
三类问题都能机械化解决，却都还靠散文规则在管：

1. **护栏误报**：`npm run check` 在干净工作树上会假红。机制是 `assertFixture` 的"不含真实痕迹"
   守卫把整段 JSON 当字符串找子串，而快照里有 10 个由 `now` 派生的 13 位毫秒时间戳，
   某个时刻它们会巧合命中 4 位禁用串（`7943` / `9063`）。这是"红灯不可信"的直接来源，
   而本项目"提交前必须全绿"的纪律完全建立在红灯可信之上。
2. **同一语义两处实现**：README 链接在 check 4 与 4b 各有一套抽取正则——窄的那套对**引用式**与
   **HTML** 两种写法完全隐形，又把**代码围栏里的示例**误报成声明
   （002 的 Lens 1 与 Lens 2 各自独立报了同一处）。
3. **规则写在散文里而不在门禁里**：`workflow/PLAN.md` 早就写了"引用位置用标题锚点、不写行号"，
   但仓库里仍有大批 `file:line`，且 001 的评审已实测到行号过期。散文规则拦不住机械违规——
   这是本项目自己的既定立场。

## 2. Non-goals

- **不改 `CHANGELOG.md`**：它记录已发布的历史，其中的行号引用是当时的现场，改它就是篡改历史。
- **不改评审报告**：`reviews/` 下是"当时看到了什么"的冻结证据，允许其行号随代码漂移。
  这正是 `REVIEW-CHECKLIST.md` 里「评审期间冻结工作树」那条规则存在的原因。
  （门禁按**任何层级的 `reviews/` 目录**豁免——豁免的是"记录"这一类东西，不是某个具体路径。）
- **不改源码注释里的行号**（`scripts/shots/*.mjs`、`scripts/check-docs.mjs` 里按行号写的那些，
  例如"零记录实测卡的文案字段在哪儿"）：那是实现者对自己刚看过的位置的就地批注，腐烂半径小、
  且不影响对外承诺。本轮只收口文档层（FR-003 的范围就是这么定的）。
- **不把 `ROADMAP.md` 的历史段落逐字重写**：只把引用形态从行号换成锚点 / 符号名，结论不动。
- **不新增依赖**：门禁与钩子都用 Node 标准库（宪法 IV）。
- **不改任何宪法原则**：但按宪法自身的修订程序把 VI 章那条陈旧的 `npm run check` 组成清单
  同步为 **v1.0.1（PATCH）** —— 清单是"订阅"而非规则本身，门禁集合变了它就该跟着变，
  否则 `AGENTS.md` 所称的"判定口径的权威"这一份会最先漂（Lens 3 的 M3）。

## 3. Premises（逐条核验，✅ = 已用命令 / 代码核实）

| # | 前提 | 核验 | 结果 |
|---|---|---|---|
| 1 | 干净工作树上 `npm run check` 会假红，且机制是**时钟巧合** | 机制：`assertFixture` 用 `JSON.stringify(snapshot).includes(banned)`，而快照里 10 个字段由 `now±常数` 派生。**确定性复现**：`now=1789716103943` 时 `throughput.byProvider[1].lastAt = now-26000 = 1789716077943` 含 `7943` → 旧版本必抛错。**配对实测**（同一 `now` 上跑新旧守卫，模拟"一轮 check-docs = 10 张快照"）：**旧整轮假红 154/10000 = 1.54%（95% CI 1.32–1.80%）**，两批合计 187/13000；新守卫 **0/13000** | ✅ |
| 2 | 假红来自"整段 JSON 当字符串找子串" + `now` 派生的 13 位毫秒时间戳 | `const now = options.now ?? Date.now()`；旧守卫 `JSON.stringify(snapshot).includes(banned)`。派生偏移共 10 个 | ✅ |
| 3 | CI 也在跑这条检查，所以假红会传染到每个 PR | `.github/workflows/ci.yml` manifest job 的 `README claims match the code` 跑 `check-docs.mjs` | ✅ |
| 4 | README 链接有**两套**抽取实现；窄的那套漏**引用式**与 **HTML** 两种写法，且对**围栏内示例**误报 | 逐字复刻 `82b6561^` 的第 4 项正则做行为矩阵（Lens 3 独立复算一致）：内联报/报、**带 title 报/报**、引用式 **放行**/报、HTML **放行**/报、围栏内旧**误报**/新放行。注意：title 形态旧实现本来就认得——"三种写法"的说法是错的 | ✅（含纠正） |
| 5 | "机械检查必须做行为矩阵且可证伪"这条规则有**三份**副本 | grep：`AGENTS.md`、`workflow/PLAN.md`、`workflow/REVIEW-CHECKLIST.md` | ✅ |
| 6 | 仓库目前**没有任何提交门禁** | 改动前：`Test-Path .githooks` = False、`git config --get core.hooksPath` 为空。**注意**：验收 T4 时临时启用过 `core.hooksPath`，收口时已撤回，仓库默认仍是不启用 | ✅（规划时） |
| 7 | 行号引用在门禁范围内确实存在 | 用**提交里那个检查器**在 `82b6561^` 的树上复算：范围内 **21 条**（`ROADMAP.md` 4、`specs/001/…/plan.md` 9、`qa-report.md` 1、`tasks.md` 7），全仓 `.md` 224 条。（早期记的"26 条"= 21 + 当时**未提交**的 `specs/003/plan.md` 草稿里那 5 个示例；"50 处"是从全仓 grep 里读的，口径不同，已废弃） | ✅（含纠正） |

**前提 1 的取证方法本身就是一条教训**：先是用 `1-(1-p)^10` 外推，得到"每轮 3.73%"——可那个式子
把一轮里的 10 张快照当成**独立事件**，而它们共用同一个时钟（`makeSnapshot({variant, lang})` 不传
`now`，各自取 `Date.now()`，整轮只跨几毫秒）。同一巧合一次命中就命中整轮，于是真实整轮率只有
**1.5%** 左右。**共享时钟的样本不能乘出来**；要报整轮率就直接模拟整轮。

**前提 1 的意义**：这不是"偶发不稳定"，而是**可复现的误报**。`AGENTS.md` 与 `PLAN.md` 都写了
"漏检或误报的检查比没有检查更糟（假安全感）"——所以这一条是第一优先级，而非附带修复。

## 4. Approach

### Considered alternatives

**FR-001 误报消除**

| 方案 | 否决理由 |
|---|---|
| A. 断言前把 `now` 钉成固定值 | 真实出图用真实时钟；钉死后守卫验的是**另一个 payload**，从此对"截图里真的出现真实痕迹"失明 |
| B. 干脆不扫数字（只扫字符串） | 丢掉最该抓的一类：fixture 里硬编码 `remaining: 7943` 就是真实余额泄漏 |
| C. **逐叶扫描 + 时钟整数豁免**（采用） | 字符串仍按子串查；数字按字符串查，但 `|n| ≥ 1e12` 的整数视为时钟毫秒值豁免——真实痕迹都不在那个量级 |
| D. 换更长的禁用串 | 治标：任何 4 位串都能被 13 位时钟命中，换串只是换一个巧合点 |

**FR-002 单源化**

| 方案 | 否决理由 |
|---|---|
| A. 把 4b 的正则复制给第 4 项 | 正是"同一语义两处实现"的复发 |
| B. **共用一个模块**（采用） | 一处实现，三个消费者（第 4 项 / 4b / 第 10 项） |
| C. 只保留 4b、删掉第 4 项 | 4b 在 `files` 缺失时整段跳过；第 4 项是那个情况下的唯一防线 |

**FR-003 行号门禁**

| 方案 | 否决理由 |
|---|---|
| A. 把 `PLAN.md` 里那句规则写得更强 | 已被证伪：规则早就在，仓库里仍有大批引用 |
| B. **新门禁 + 保留 `PLAN.md` 那句作为产出方说明**（采用） | 产出（PLAN）与校验（门禁 + Lens 1）配对 |
| C. 门禁也扫源码注释 | 非目标：腐烂半径小，且会把改动面从 21 处扩到 50+ 处 |

**FR-004 提交门禁**

| 方案 | 否决理由 |
|---|---|
| A. 装好钩子并直接 `git config core.hooksPath` | 一次改动静默改变所有协作者的提交行为 |
| B. **提供 `.githooks/pre-commit` + 文档里一行启用命令**（采用） | 想用的人一行启用；默认不启用是**刻意的**，写进文档而非靠猜 |
| C. 只依赖 CI | 假红的代价在 CI 上放大到每个 PR；本地钩子让红灯提前到提交前 |

### Chosen approach and why

**把"可靠性"本身当成产品来修**：这条线贯穿全部 FR——凡是"能机械判定的"就不靠散文规则
（FR-003）、凡是"同一语义"就只留一处实现（FR-002/FR-005）、凡是"门禁"就必须自带行为矩阵且
可证伪（新增 `test/guards.mjs`）。理由是它们都属于同一类缺陷：**检查器本身出错时，
没有任何东西会告诉你它错了**。

第二条线是**把"机制"与"订阅"分开**：`npm run check` 的组成清单在四份文档里出现过
（`AGENTS.md`、`constitution.md`、`release.mjs`、两份 README），它们都只是 `package.json#scripts.check`
的**订阅**，天然会漂。收敛办法是让每一份都指向那个唯一源头，或在改动时同步。

第三条线是**只在能给出证据的地方下结论**：本计划里每个数字都带取证方式（哪条命令、哪个提交、
多少样本），因为这个项目已经吃过两次"数字看着对但其实算错了"的亏（3.73% 的错误外推、
26 vs 21 的口径混淆）。

## 5. Design

改动的落点与职责（`§9 Steps` 是执行顺序）：

| 文件 | 改什么 | 为什么在这里 |
|---|---|---|
| `scripts/shots/fixture.mjs` | `assertFixture` 的痕迹比对改**逐叶 + 时钟整数豁免**；新增 `BANNED_TRACES` / `isClockMillis` / `collectLeaves`（含对象 key） | 守卫住在它测的那份数据旁边；`makeSnapshot()` **零改动**（§8 的 T6 证明） |
| `scripts/link-targets.mjs`（新） | `extractLinkTargets` / `extractImageTargets` / `stripTarget` / `normalizeTarget` / `classifyTarget` | 从 `check-docs.mjs` **搬出来**才可被测试 import（`check-docs.mjs` 是顶层执行脚本，import 它就等于跑全套） |
| `scripts/check-docs.mjs` | 第 4 / 4b / 第 10 项改为消费 `link-targets.mjs`；**只有 `relative` 才允许 `existsSync`** | 它不再自己持有正则或越界判定，杜绝与 4b 再次分叉 |
| `scripts/check-refs.mjs`（新） | `findLineRefs`（两段式线性扫描）+ 手工 `walkMarkdown`（跳过 reparse point） | 门禁本体；纯函数部分导出以便常驻测试 |
| `test/guards.mjs`（新） | 三处门禁的**常驻**行为矩阵（含"不得退化成二次方"与越界不变式） | 矩阵只写在规格里会随会话结束失去约束力 |
| `.githooks/pre-commit`（新） | 跑 `npm run check`；**默认不启用** | 见 §4 的 FR-004 备选表 |
| `package.json` / `.github/workflows/ci.yml` / `scripts/release.mjs` | 两处新门禁接线；且进去三平台矩阵 | 只接一处 = 未接线的检查 |
| `AGENTS.md` | 删掉"机械检查也是代码"那段（三份 → 两份）；Commands 列表同步 | 它每个会话都占上下文，而那段只是复述 |
| `workflow/ENVIRONMENT.md`（新） | 本仓库的环境事实（远端别名、tag 与浅克隆、出图机前置、pwsh 后果） | 分支罕见的材料放指针后面 |
| `CONTRIBUTING.md` / `README.md` / `README.en.md` / `constitution.md` | `npm run check` 组成清单四处同步；宪法按修订程序 → v1.0.1 | 它们是同一份事实的订阅 |
| `specs/001-…`（plan / tasks / qa-report）、`ROADMAP.md` | 只在范围内把行号引用换成锚点 / 符号名 | FR-003 的存量 |

**复用检查**：`extractLinkTargets` / `classifyTarget` 是**取代**两套旧正则（grep 确认仓库里没有
第三套 `](…)` 抽取）；`findLineRefs` 的两段式扫描取代一条二次方正则；"行为矩阵 + 可证伪"这条规则
从三份收敛到两份（产出方 `PLAN.md` + 校验方 `REVIEW-CHECKLIST.md`）。

## 6. Failure modes

| 失败模式 | 长什么样 | 接住机制 |
|---|---|---|
| **新门禁自己误报** | 刚加的检查像 FR-001 一样假红 | 每条新/改门禁的测试计划必须含"应当放行"用例；FR-001 的行为矩阵就是被误报打脸后的产物 |
| **检查写了但没接线** | 新脚本只加进 `npm run check`，忘了 CI / release 路径 | §9 把"接进多处"写成同一步；Lens 3 核 diff 文件清单（正是它抓到 `release.mjs` 漏接） |
| **修引用时改坏语义** | 把行号换成锚点时顺手把结论也改了 | 只换形态不改结论；Lens 1 逐条复核替换后的引用仍指向同一事物 |
| **用错误的方法得到"对"的结论** | 用乘法外推整轮假红率（本轮真实发生） | 前提必须写**取证方式**；共享时钟的样本不许乘；Lens 3 独立复算每个前提 |
| **空数据伪装成结论** | 旧检查器副本没生成成功，于是"旧实现全都漏检"（本轮真实发生） | 取证脚本必须先自证（`node --check`、blob 逐字节比对）再采信 |
| **顺手扩大范围** | 顺手把 reviews/ 与源码注释也扫了 | 非目标在 §2 写死；门禁的豁免面是显式的、且与 spec 措辞对齐 |
| **假绿** | 新门禁一个违规都找不到，其实正则写错了 | 可证伪：在修复前提下车必须报红（§8 T3 记录了实际红线数）；另有扫描面下限断言 |

## 7. UI states

不适用：本规格不含 UI 改动。FR-001 只改**守卫的判定方式**，`makeSnapshot()` 的输出不受影响——
由 §8 的 T6 证明（源码层 hunk 全在 `assertFixture` 及其上方；行为层固定 `now` 下逐字节相同）。
